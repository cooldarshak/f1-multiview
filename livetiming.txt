6. VERIFIED SOURCE FINDINGS TO INVESTIGATE

These findings were observed in the recorded branch. Revalidate them against the current branch before changing code.

Finding A: replay loading can be skipped

In "MultiViewViewModel.kt":

- "setSession()" resets timing state and calls "loadStreams(session)", but does not itself call "loadReplayTiming(session)".
- Separate VOD/resume paths do call "loadReplayTiming(session)".
- "loadReplayTiming()" returns immediately when "seasonYear" or "meetingNumber" is missing.
- "updateReplayTiming()" returns immediately if the replay client has not loaded data.
- "App.kt" polls the replay player's playhead and invokes "updateReplayTiming()".

Potential result: a replay can show no timing without an informative error, because the replay data loader was never started or session metadata was missing.

Required fix:

1. Trace every session-entry path.
2. Ensure eligible replay sessions always initiate timing archive resolution and loading.
3. Resolve missing identifiers where possible using existing session/meeting metadata.
4. Set explicit loading, ready and unavailable states.
5. Never silently return while leaving an indefinite loading/empty screen.
6. Keep replay state separate from live timing state.

Finding B: replay session selection is too permissive

"ReplayTimingClient.kt" currently chooses the first archive session whose name contains the requested name OR whose type matches.

This can select the wrong session when practice, qualifying, sprint qualifying and other session names overlap.

Required fix:

- Implement a deterministic session resolver.
- Prefer exact identifiers and exact names.
- Use meeting, season, session title and session type as supporting evidence.
- Rank candidates using a documented score.
- Reject ambiguous matches instead of quietly loading a different session.
- Log the chosen archive path, selected session metadata and reason for selection.
- Add unit tests for ambiguous names, matching types, missing metadata and exact matches.

Finding C: bundled circuit geometry is available

The current asset:
"app/src/main/assets/circuit_geometry_2026.json"

was inspected and contains 23 circuits, including:

- Sakhir/Bahrain, key "63", with 730 centreline points.
- Singapore, key "61", with 544 centreline points.

The geometry client currently attempts remote geometry sources and historical-year fallbacks before its bundled catalogue is used. Remote failures such as HTTP 401 can therefore delay or obstruct a map that could already be rendered from local data.

Required fix:

1. Resolve known circuit keys against validated bundled geometry immediately.
2. Use remote sources when local matching fails or a verified newer geometry is needed.
3. Validate circuit identity, centreline size and geometry integrity.
4. Never accept an older geometry merely because it has enough points; verify that it belongs to the correct circuit.
5. Ensure the selected live/replay session controls circuit selection correctly.
6. Add tests for circuit-key matching, aliases, unknown circuits and remote HTTP 401.
7. Confirm that position coordinates can actually be transformed into the geometry's coordinate system.

A screenshot previously showed "Circuit lookup HTTP 401", but the recorded branch's geometry request emitted "Circuit geometry HTTP 401". Verify the installed APK's commit and the actual failing request before assuming the screenshot comes from this exact code.

Finding D: live position parsing already exists, but end-to-end flow is unproven

"LiveTimingClient.kt" has a "parsePosition()" implementation that:

- Searches nested JSON structures for "Position" and "Entries".
- Reads numeric X/Y/Z coordinates.
- Stores recent trails.
- Updates driver positions.
- Publishes parsed positions.

The client also parses driver metadata and logs driver-list updates.

However, this does not prove that:

- Position messages are actually received.
- Subscription to the required feed succeeded.
- The compressed payload format was decoded correctly.
- Real position data reaches the UI.
- The coordinates match the selected circuit geometry.

Required fix:
Instrument the actual chain:
connection → negotiation → subscription → raw message → decompression → feed name → parser → valid entries → ViewModel state → rendered markers.

Use counters, timestamps and source-derived values. Do not log credentials, cookies or licence secrets.

"UgisInfoPanel.kt" already renders timing rows, but the presentation does not yet fully reproduce the reference timing tower.

Implement a dedicated native Compose timing tower with:

Finding G: the map needs timestamp-based interpolation

"TrackMapPanel.kt" already draws circuit geometry, driver markers and trails. The rendering does not yet demonstrate the continuous, timestamp-based interpolation needed for smooth motion between incoming position updates.

Required fix:

- Use actual position samples as interpolation endpoints.
- Interpolate between samples according to timestamps.
- Bound the interpolation/extrapolation horizon.
- Detect stale positions and gaps.
- Handle replay seeks and backward time movement.
- Clear or recompute trails when a replay seek invalidates their history.
- Ensure marker positions align with the selected circuit.
- Never generate artificial GPS coordinates to make markers move.
